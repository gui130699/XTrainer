================================================================================
1. OBJETIVO DO PRODUTO
================================================================================

XTrainer é um PWA pessoal de musculação. O usuário cria seus próprios treinos, executa
séries, registra peso e avaliações e consulta evolução. O usuário não cadastra exercícios
globais. Essa responsabilidade pertence ao XTrainer Admin.

XTrainer Admin é um PWA separado e deliberadamente pequeno. Seu escopo é:
- consultar identificação mínima das contas cadastradas;
- listar, pesquisar e filtrar exercícios;
- cadastrar e editar exercícios;
- ativar/desativar exercícios;
- substituir o catálogo pelo dataset canônico;
- exportar CSV;
- registrar auditoria administrativa.

O Admin não possui abas de treinos, sessões, evolução ou avaliações e não recebe acesso
às collections privadas correspondentes.

7. SECURITY RULES — FIRESTORE
================================================================================

Funções centrais:
- signedIn(): request.auth != null;
- isAdmin(): system/config.adminUid == request.auth.uid;
- ownsExisting(): resource.data.ownerId == request.auth.uid;
- createsForSelf(): request.resource.data.ownerId == request.auth.uid;
- preservesOwner(): ownerId não muda.

Política por collection:
- system/config: read true; create/update/delete false;
- users: próprio usuário ou admin lê; usuário cria role user; edita whitelist;
- exercises: autenticado lê; admin cria/edita/exclui;
- workouts: somente owner;
- workoutSessions: somente owner + validação de status/ID/transição;
- bodyWeights: somente owner + peso positivo;
- physicalAssessments: somente owner + campos tipados;
- auditLogs: admin lê/cria; update/delete negados;
- qualquer outra collection: negada por não existir match permissivo.

Validação de sessão:
- documento active precisa ser active-{request.auth.uid};
- completed/cancelled pode usar ID histórico;
- ownerId é imutável;
- completed/cancelled não retorna a active;
- payload aceita somente os campos declarados.

Validação testada no emulador:
- cliente não cria/troca system/config;
- usuário não se promove a admin;
- usuário não lê dados de outro;
- usuário não escreve exercícios;
- ownerId não muda;
- active aleatória é negada;
- histórico não reabre;
- avaliação parcial tem CRUD apenas pelo dono;
- admin não lê collections privadas;
- audit log é imutável;
- collection desconhecida é negada.

12. SESSÃO ATIVA E SINCRONIZAÇÃO
================================================================================

ID ativo: active-{uid}.

Início:
- transaction.get do ID fixo;
- se existir, erro amigável de sessão já em andamento;
- se não existir, transaction.set com serverTimestamp;
- a UI recebe snapshot local imediatamente.

Retrocompatibilidade:
- primeiro procura o ID fixo;
- depois consulta sessões antigas ownerId/status active;
- transação move a primeira para o ID fixo;
- duplicatas antigas são canceladas;
- nada é migrado destrutivamente em lote.

Durante a sessão:
- digitação de carga/reps é local;
- sincronização ocorre em blur e em ações relevantes;
- concluir/desfazer/adicionar/remover set persiste estado;
- status: alterações locais, salvando, salvo, erro, offline;
- erro oferece tentativa novamente;
- nenhuma write é disparada em cada tecla.

Descanso:
- persiste restEndsAt Timestamp;
- contador é derivado de restEndsAt - relógio atual;
- recarregar página recupera o tempo restante;
- pular remove o campo;
- +15s altera o timestamp final.

Finalização:
- transaction lê active;
- cria histórico completed com auto-ID;
- endedAt usa serverTimestamp;
- duração é calculada desde startedAt;
- remove documento active;
- abre resumo com duração, volume, sets, exercícios e recordes.

Cancelamento:
- cria histórico cancelled;
- remove active na mesma transação;
- cancelled não entra no dashboard, histórico completed ou analytics.

13. HISTÓRICO E DASHBOARD
================================================================================

Query canônica de histórico:
ownerId == uid
status == completed
orderBy startedAt desc
limit 20/100
startAfter cursor

Dashboard mensal usa intervalo do primeiro dia do mês ao primeiro dia do próximo mês.
Compara mês e ano, evitando misturar agosto de anos diferentes.

Métricas:
- workouts: quantidade de sessões completed do mês;
- sets: totalSets dessas sessões;
- volume: totalVolume dessas sessões;
- streak: semanas consecutivas com treino, começando na atual ou na imediatamente anterior;
- records: máximos calculados do histórico carregado.

Estados loading/error/empty são separados. Erros de permissão, rede, autenticação e
índice faltante são convertidos para instruções compreensíveis.

15. ANALYTICS E EVOLUÇÃO POR EXERCÍCIO
================================================================================

Fonte única: workoutSessions status completed.

Identidade:
- exerciseId é chave primária;
- snapshots antigos sem ID usam fallback cauteloso legacy:nome-normalizado;
- nome é exibido, não usado como chave normal quando há ID.

Somente sets completed entram nos cálculos.

Fórmulas:
- volume do set = load * reps;
- volume da sessão/exercício = soma dos sets concluídos;
- carga máxima = maior load concluído;
- repetições máximas = maior reps de um set concluído;
- melhor série = maior carga; em empate, maior reps;
- evolução absoluta = atual - primeiro;
- evolução percentual = (atual - primeiro) / primeiro * 100;
- se primeiro == 0, percentual é null para evitar divisão inválida.

Recordes derivados:
- maior carga;
- maior número de reps;
- maior volume em uma sessão;
- melhor série;
- data de cada marco.

Não existe cadastro manual de PR. O resumo de treino detecta novos recordes comparando
a sessão finalizada com as sessões anteriores.

21. SISTEMA DINÂMICO DE MÉTODOS DE TREINO (18/08/2026)
================================================================================

O catálogo global trainingMethods contém 24 métodos padrão e aceita métodos personalizados seguros criados pelo Admin. Cada definição possui categoria, motor, capacidades, regras, esquema de campos, padrões, ordem, estado e versão.

O usuário seleciona somente métodos ativos ao montar o treino. WorkoutExercise e WorkoutExerciseGroup gravam methodConfig e methodSnapshot. A sessão copia esses snapshots e gera TrainingSet detalhado com bloco, etapa, papel, duração, cadência, descanso e indicador de falha quando aplicável. Treinos antigos sem método continuam como Séries normais.

Motores disponíveis: normal, group, drop, rest-pause, cluster, progression, top-backoff, tempo, failure, amrap, isometric, partials, myo-reps e time.

O Admin possui as rotas /metodos e /sistema. /metodos oferece filtros, indicadores, wizard visual, edição de esquema seguro, padrões, duplicação, ordem, ativação/desativação, sincronização idempotente e auditoria. Não são aceitos JavaScript, HTML nem eval.

Grupos de exercício usam WorkoutExerciseGroup, groupId e groupPosition. A execução é exibida por rodada. O descanso entre exercícios e o descanso após a rodada são independentes; o descanso longo ocorre somente depois do último membro.

Analytics contam todas as etapas especiais concluídas, mas excluem aquecimento e aproximação de métricas efetivas e recordes. O histórico mantém todos os dados.

As regras do Firestore permitem leitura de trainingMethods somente a autenticados e escrita apenas ao administrador. Os 24 padrões e as regras foram publicados no projeto xtrainer-45f8d.

Detalhes técnicos, arquivos e resultados de testes: RELATORIO_IMPLEMENTACAO_METODOS.md.
