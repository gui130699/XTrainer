================================================================================
1. OBJETIVO DO PRODUTO
================================================================================

XTrainer é um PWA pessoal de musculação. O usuário cria seus próprios treinos, executa
séries, registra peso e avaliações e consulta evolução. O usuário não cadastra exercícios
globais. Essa responsabilidade pertence ao XTrainer Admin.

XTrainer Admin é um PWA separado e deliberadamente pequeno. Seu escopo é:
- consultar identificação mínima das contas cadastradas;
- listar, pesquisar e filtrar exercícios;
- cadastrar e editar exercícios;
- ativar/desativar exercícios;
- substituir o catálogo pelo dataset canônico;
- exportar CSV;
- registrar auditoria administrativa.

O Admin não possui abas de treinos, sessões, evolução ou avaliações e não recebe acesso
às collections privadas correspondentes.

7. SECURITY RULES — FIRESTORE
================================================================================

Arquivo: firestore.rules (não alterado nesta sessão).

Funções centrais:
- signedIn(): request.auth != null;
- isAdmin(): system/config.adminUid == request.auth.uid;
- ownsExisting(): resource.data.ownerId == request.auth.uid;
- createsForSelf(): request.resource.data.ownerId == request.auth.uid;

Política por collection:
- system/config: read true; create/update/delete false;
- users: próprio usuário ou admin lê; usuário cria role user; edita whitelist;
- exercises: autenticado lê; admin cria/edita/exclui;

- workouts: somente owner;
- workoutSessions: somente owner + validação de status/ID/transição;
- bodyWeights: somente owner + peso positivo;
- physicalAssessments: somente owner + campos tipados;
- auditLogs: admin lê/cria; update/delete negados;
- qualquer outra collection: negada por não existir match permissivo.

OBSERVAÇÃO IMPORTANTE (nova nesta versão): as funções validUser() e validAssessment()
ainda listam photoURL e photos, respectivamente, como campos OPCIONAIS permitidos.

Validação de sessão:

- completed/cancelled pode usar ID histórico;
- ownerId é imutável;
- completed/cancelled não retorna a active;

8. REMOÇÃO DO FIREBASE STORAGE E DOS CAMPOS DE FOTO (NOVO NESTA VERSÃO)
================================================================================

Motivo: o plano gratuito do Firebase não provisiona Cloud Storage de forma confiável
sem cobrança/billing configurado, e as chamadas de upload (uploadBytes) ficavam
pendentes indefinidamente quando o bucket não respondia — nunca rejeitavam, então o
try/catch/finally do formulário nunca era acionado. Na prática, isso travava a tela de
Perfil em "SALVANDO..." para sempre sempre que o usuário selecionava uma foto, mesmo
que o restante dos dados pessoais estivesse válido.

O que foi removido do código-fonte do XTrainer:
- campo de upload de foto e exibição de avatar em /perfil;
- os três campos de foto (frente/lateral/costas) na avaliação física avançada em
  /evolucao, incluindo o input de arquivo e o bloco <details>Fotos</details> em
  src/components/assessment-form.tsx;
- função uploadProfilePhoto em src/services/auth.ts;
- função assessments.uploadPhoto em src/services/data.ts;
- import e uso de firebase/storage em src/lib/firebase.ts (a instância "storage" não é
  mais exportada);
- campo photoURL de UserProfile e campo photos de PhysicalAssessment em
  src/types/index.ts;
- normalização de raw.photos em src/lib/compatibility.ts;
- storage.rules foi apagado do repositório e a chave "storage" removida de
  firebase.json — o Firebase Storage deixou de fazer parte do deploy deste projeto.

O que NÃO foi feito (fora do escopo de uma alteração de código):
- o bucket do Cloud Storage do projeto xtrainer-45f8d no Console Firebase não foi
  excluído nem desabilitado — só parou de ser referenciado pelo app;
- fotos que já tenham sido enviadas por algum usuário antes desta mudança (se alguma
  chegou a funcionar) continuam no bucket e nos documentos antigos; elas simplesmente
  não são mais lidas nem exibidas pelo app, e os campos correspondentes nas regras do
  Firestore continuam aceitos como legado (seção 7).

Efeito colateral positivo: o bundle do app ficou menor (o SDK do Firebase Storage e o
código de upload não são mais incluídos), e uma fonte inteira de travamento silencioso
foi eliminada.

12. SESSÃO ATIVA E SINCRONIZAÇÃO (REVISADO NESTA VERSÃO)
================================================================================

ID ativo: active-{uid}.

Início:
- transaction.get do ID fixo;
- se existir, erro amigável de sessão já em andamento;
- se não existir, transaction.set com serverTimestamp;
- a UI recebe snapshot local imediatamente.

Retrocompatibilidade:
- primeiro procura o ID fixo;
- depois consulta sessões antigas ownerId/status active;
- transação move a primeira para o ID fixo;
- duplicatas antigas são canceladas;
- nada é migrado destrutivamente em lote.

Durante a sessão — o que mudou nesta versão:
Antes, o indicador de status de sincronização era calculado torcendo a promise de cada
updateDoc individual (setSyncStatus dentro de then/catch da própria chamada de
gravação). Isso funcionava bem com internet estável, mas em wifi de academia instável o
navigator.onLine podia reportar "online" mesmo sem conectividade real, fazendo a tela
ficar presa em "Salvando..." indefinidamente até a promise (que só resolve quando o
servidor confirma) eventualmente resolver ou nunca resolver enquanto a aba ficasse
aberta.

Desde esta versão, sessions.watchSyncState (src/services/data.ts) assina apenas os
METADADOS do documento da sessão ativa via onSnapshot(..., {includeMetadataChanges:
true}), lendo snapshot.metadata.hasPendingWrites. Esse campo, mantido internamente pelo
próprio SDK do Firestore, indica com precisão se a última alteração feita neste
dispositivo já foi confirmada pelo servidor ou ainda está apenas no cache local (por
estar offline ou por lentidão de rede). Combinado com eventos reais online/offline do
navegador (window.addEventListener("online"/"offline")), o status exibido na tela de
treino (src/app/treino/page.tsx) passou a ser:
- "offline" (Salvo neste dispositivo. Aguardando sincronização.) quando o navegador
  está desconectado;
- "saving" (Salvando...) quando online mas ainda há escritas pendentes de confirmação;
- "saved" (Salvo) quando online e sem escritas pendentes;
- "error" (com botão Tentar novamente) apenas quando sessions.save() realmente rejeitar
  (ex.: permission-denied), nunca por estar offline.

Como o cache local do Firestore já é persistente (persistentLocalCache, ver seção 17),
as escritas feitas offline (marcar série, ajustar descanso etc.) sempre ficam
registradas neste aparelho e são reenviadas automaticamente quando a conexão volta,
inclusive se o app for fechado e reaberto no meio do processo — isso já era garantido
pela configuração existente do Firestore; o que mudou foi o indicador de status passar a
refletir essa realidade com precisão, em vez de depender do timing da promise de cada
chamada individual.

Descanso:
- persiste restEndsAt Timestamp;
- contador é derivado de restEndsAt - relógio atual;
- recarregar página recupera o tempo restante;
- pular remove o campo;
- +15s altera o timestamp final;
- notificação do navegador mostra o tempo restante e avisa quando o descanso termina
  (ver seção 17).

Finalização:
- transaction lê active;
- cria histórico completed com auto-ID;
- endedAt usa serverTimestamp;
- duração é calculada desde startedAt;
- remove documento active;
- abre resumo com duração, volume, sets, exercícios e recordes.
Observação: finish()/cancel() usam transaction, que exige conectividade real com o
servidor — diferente das gravações incrementais de série, finalizar ou cancelar uma
sessão não é uma operação que fica "pendente" offline; se a rede cair no meio dessa
chamada específica, o erro amigável de rede é exibido (dataErrorMessage) e o usuário
pode tentar novamente quando a conexão voltar.

Cancelamento:
- cria histórico cancelled;
- remove active na mesma transação;
- cancelled não entra no dashboard, histórico completed ou analytics.

- volume: totalVolume dessas sessões;
- peso atual: última pesagem registrada (bodyWeights);
- streak: semanas consecutivas com treino, começando na atual ou na imediatamente
  anterior;
- records: máximos calculados das últimas 100 sessões completed carregadas.

Estados loading/error/empty são separados. Erros de permissão, rede, autenticação e
índice faltante são convertidos para instruções compreensíveis (dataErrorMessage em
src/lib/utils.ts).

14. EVOLUÇÃO CORPORAL E AVALIAÇÕES
================================================================================

Peso:
- registrar, editar e excluir;
- data, kg, observação;
- origem manual ou assessment;
- gráfico e histórico;
- filtros 30/90/180/365/tudo;
- fonte canônica bodyWeights.

Avaliação rápida:
- data;
- peso, altura, gordura, massa gorda e massa magra opcionais;
- observação;
- opção de também registrar peso oficial.

Avaliação completa:
- todos os campos rápidos;
- medidas corporais agrupadas;
- nenhum campo corporal é obrigatório.

Avaliação avançada:
- medidas;
- dobras cutâneas;
- protocolo (Jackson-Pollock 3 ou 7 dobras);
- cálculo de composição corporal (gordura, massa gorda, massa magra) pela equação de
  Siri a partir da densidade corporal;
- SEM campos de foto (removidos nesta versão — o bloco "Fotos" que existia no formulário
  de avaliação avançada foi retirado por completo, ver seção 8);
- não calcula percentual de gordura com fórmula inventada — usa protocolos
  antropométricos padrão e deixa claro que é uma estimativa, não substitui avaliação
  clínica.

Comparação:
- escolhe Avaliação A e B;
- mostra valor anterior, posterior e diferença;
- compara somente campos presentes em ambas;
- unidades kg, %, cm ou mm.

Readers aceitam documentos antigos sem type/measurements/skinfolds/fatMass/source (ver
seção 19). Documentos antigos que ainda tenham o campo "photos" simplesmente não
exibem mais essas fotos — o campo é ignorado pela normalização atual.

15. ANALYTICS E EVOLUÇÃO POR EXERCÍCIO
================================================================================

Fonte única: workoutSessions status completed.

Identidade:
- exerciseId é chave primária;
- snapshots antigos sem ID usam fallback cauteloso legacy:nome-normalizado;
- nome é exibido, não usado como chave normal quando há ID.

Somente sets completed entram nos cálculos.

Fórmulas:
- volume do set = load * reps;
- volume da sessão/exercício = soma dos sets concluídos;
- carga máxima = maior load concluído;
- repetições máximas = maior reps de um set concluído;
- melhor série = maior carga; em empate, maior reps;
- evolução absoluta = atual - primeiro;
- evolução percentual = (atual - primeiro) / primeiro * 100;
- se primeiro == 0, percentual é null para evitar divisão inválida.

Recordes derivados:
- maior carga;
- maior número de reps;
- maior volume em uma sessão;
- melhor série;
- data de cada marco.

Não existe cadastro manual de PR. O resumo de treino detecta novos recordes comparando
a sessão finalizada com as sessões anteriores (detectNewRecords em
src/lib/training-analytics.ts).

17. PWA, CACHE E OFFLINE
================================================================================

O XTrainer possui:
- manifest.webmanifest;
- ícones 192, 512 e maskable-512 (xtrainer-user-icon-*);
- display standalone;
- metadata/appleWebApp com apple-touch-icon;
- botão de instalação (src/components/install-app-button.tsx), com ajuda específica
  para iOS via Compartilhar > Adicionar à Tela de Início;
- service worker (public/sw.js) com estratégia network-first para navegação e
  cache-first com atualização em segundo plano para os demais assets;
- registro do service worker com updateViaCache: "none" e recarregamento automático da
  página quando um novo controller assume (src/components/providers.tsx).

Cache do service worker:
- nome do cache é xtrainer-user-{BUILD_VERSION}, onde BUILD_VERSION é o SHA do commit
  publicado (injetado via NEXT_PUBLIC_BUILD_VERSION no build e substituído em
  public/sw.js e public/manifest.webmanifest antes do deploy);
- na ativação, qualquer cache antigo com prefixo xtrainer-user- e nome diferente do
  atual é apagado — isso troca automaticamente a cada novo deploy, sem precisar de um
  número de versão manual como em versões anteriores do projeto.

Notificações do cronômetro de descanso (Web Notifications API, via Service Worker):
- o usuário precisa conceder permissão explicitamente (botão "Ativar notificações do
  cronômetro de descanso" na tela de treino quando a permissão ainda está no estado
  "default");
- enquanto há descanso em andamento, uma notificação silenciosa (tag "xtrainer-rest")
  mostra o tempo restante e é substituída (não duplicada) a cada atualização;
- ao zerar, uma notificação com renotify dispara um alerta ("Descanso finalizado! Hora
  da próxima série");
- a notificação é fechada automaticamente ao finalizar ou cancelar a sessão;
- "renotify" existe na Notification API dos navegadores mas não está tipado em
  lib.dom.d.ts do TypeScript instalado — há uma extensão de tipo local
  (ExtendedNotificationOptions) em src/app/treino/page.tsx para contornar isso sem usar
  "any".

Offline e sincronização:
- Firestore usa persistentLocalCache com persistentMultipleTabManager — todas as
  leituras e escritas ficam disponíveis em IndexedDB local, sobrevivendo a fechar o
  navegador e sincronizando automaticamente quando a conexão volta;
- a tela de treino expõe esse estado de forma precisa via hasPendingWrites (seção 12);
- finalizar/cancelar uma sessão exige uma transação com o servidor e não fica
  "pendurada" offline como as gravações incrementais de série;
- o sistema não promete offline total: operações que dependem de uma resposta imediata
  do servidor (como iniciar uma sessão, que verifica se já existe uma ativa) ainda
  precisam de conectividade real para completar com segurança.

Tratamento de erros de carregamento de página (novo nesta versão):
- src/app/error.tsx: error boundary por rota, dentro do layout normal, oferece
  "Tentar novamente" (reset) e "Voltar ao início";
- src/app/global-error.tsx: error boundary de última instância, substitui todo o
  layout raiz (inclusive <html>/<body>) com estilos inline autocontidos, para o caso
  raro de um erro no próprio layout impedir o app de renderizar.

21. EXPORTAÇÃO DE HISTÓRICO — CSV E PDF (NOVO NESTA VERSÃO)
================================================================================

Onde: botões "Exportar CSV" e "Exportar PDF" no topo do card de filtros da tela
/historico (src/app/historico/page.tsx).

Lógica pura extraída para src/lib/history-export.ts (sem dependência de React ou
Firebase, para poder ser testada com node:test):
- sessionMatchesFilters(session, filters): mesma lógica de filtro por período/treino/
  exercício usada na tela, reaproveitada tanto para a lista visível quanto para a
  exportação;
- buildExportRows(sessions, formatDate): converte sessões concluídas em uma linha por
  série CONCLUÍDA (séries não concluídas são ignoradas), com data, treino, exercício,
  etapa (trainingStageLabel — ex.: "Aquecimento", "Falha", "Drop 2"), carga, reps ou
  duração, volume, RPE e RIR;
- csvEscape / rowsToCsvText: geram o texto do CSV (separador ";", aspas quando o valor
  contém ; , " ou quebra de linha) sem depender de Blob/DOM, para ser testável.

Fluxo de exportação (na página, que lida com DOM/navegador):
1. busca TODO o histórico completed do usuário via sessions.listAllCompleted (não
   apenas a página de 20 itens carregada na tela);
2. aplica os mesmos filtros ativos na tela (período/treino/exercício);
3. se não sobrar nenhuma linha, mostra "Nenhuma sessão para exportar com os filtros
   atuais." em vez de gerar um arquivo vazio;
4. CSV: monta o texto com rowsToCsvText, adiciona um BOM UTF-8 no início (para acentos
   abrirem corretamente no Excel) e dispara o download via Blob + <a download>;
5. PDF: importa jsPDF e jspdf-autotable DINAMICAMENTE (import() dentro da função, não
   no topo do arquivo) — assim essas duas bibliotecas (~400 KB) só entram no bundle do
   navegador quando o usuário realmente clica em "Exportar PDF", e não pesam no
   carregamento normal da tela de histórico. Gera uma tabela paisagem com cabeçalho,
   data de exportação, contagem de séries e a mesma tabela de colunas do CSV.

Dependências novas em package.json: jspdf e jspdf-autotable (instaladas nesta sessão).

Testado em tests/history-export.test.ts (5 casos): filtro por período relativo a um
horário de referência, filtro por treino e por exercício (ignorando acentos), geração
de linhas só a partir de séries concluídas, escape de CSV e formatação do texto final.

- frontend não lista/exclui contas de Firebase Authentication;

- App Check não foi ativado remotamente;
- nenhuma fórmula clínica/profissional de gordura corporal é calculada — são estimativas
  antropométricas padrão;

  seção 8) — qualquer necessidade futura de fotos exigiria reativar Storage com
  billing configurado (plano Blaze) no Firebase, ou usar um provedor externo.

33. MÓDULO SAÚDE E TERAPIAS E REFERÊNCIA DE SUBSTÂNCIAS (2026-08-22)
================================================================================

Objetivo: permitir que o usuário registre terapias/medicações já prescritas ou
informadas por ele mesmo, com agenda, lembretes, histórico e exportação para
calendário. O aplicativo NÃO prescreve medicamentos, NÃO recomenda substâncias, NÃO
determina dose, NÃO determina frequência e NÃO cria protocolos — todo dado de
substância, quantidade e frequência é digitado pelo próprio usuário; o sistema apenas
organiza, calcula o calendário local, lembra e registra o que já aconteceu.

Rotas novas no XTrainer: /saude (terapias privadas) e /referencia (biblioteca
educativa global, arquiteturalmente separada — sem vínculo automático com as
terapias privadas do usuário). Rota nova no XTrainer-Admin: /substancias (CRUD da
biblioteca educativa).

Collections novas:

- therapies (privada, somente owner): nome, início, data final ou contínua, status
  (active/paused/completed), lista de medicamentos com frequência (intervalo em
  dias, dias da semana ou datas personalizadas), observações, lembrete opcional.
- therapyAdministrations (privada, somente owner): um documento por registro de
  confirmação/pulo/adiamento — nunca para datas futuras ainda não resolvidas. O
  calendário futuro é sempre calculado localmente (src/lib/therapy-schedule.ts),
  nunca persistido com antecedência, para não gerar milhares de documentos.
- substanceReferences (global, leitura para autenticados, escrita somente admin):
  nome, nome canônico, aliases, classe, descrição, mecanismo/função geral, uso
  médico/histórico, categorias de risco (riskTags) e fontes. Não contém dose,
  intervalo, ciclo, stack nem combinação recomendada.

Funções puras testadas (tests/therapy-schedule.test.ts,
tests/therapy-calendar-export.test.ts, tests/substance-analysis.test.ts):

- calculateScheduleDates/calculateNextAdministration/calculateDueAdministrations/
  calculateOverdueAdministrations (src/lib/therapy-schedule.ts) — geram e filtram
  datas previstas sem depender do Firestore; terapias contínuas sempre respeitam um
  horizonte finito informado pelo chamador (nunca geram data infinita).
- buildTherapyCalendarEvents/buildIcsFile/buildTherapyIcs
  (src/lib/therapy-calendar-export.ts) — exportação para .ics com horizonte
  limitado (padrão 90 dias para terapias contínuas), para lembretes via calendário
  do sistema operacional, já que o PWA é estático no GitHub Pages e não tem
  notificação agendada confiável com o app fechado.
- analyzeSubstanceReferenceOverlap (src/lib/substance-analysis.ts) — conta apenas
  categorias de risco compartilhadas entre substâncias selecionadas pelo usuário na
  tela de referência; nunca classifica combinação como seguros/segura ou recomenda
  uso conjunto.

Notificações: reutiliza a infraestrutura já usada pelo cronômetro de descanso
(helper extraído para src/lib/notifications.ts, também usado por src/app/treino/
page.tsx). Ao abrir /saude com permissão concedida, uma notificação resume quantos
registros estão previstos para o dia; documentado que isso só funciona com o app
aberto — não há push confiável com o PWA totalmente fechado nesta arquitetura
estática.

Firestore Rules: matches explícitos para therapies (owner-only), therapyAdministra-
tions (owner-only) e substanceReferences (signedIn read / admin write), sem
catch-all. Testes de regra novos em tests/firestore.rules.test.mjs cobrem
privacidade (admin não lê terapias de ninguém) e escrita restrita da biblioteca.
